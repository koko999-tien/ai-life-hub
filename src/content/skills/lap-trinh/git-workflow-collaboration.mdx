          ## 1. So Sánh 3 Mô Hình Phân Nhánh
          | Mô hình | Ưu điểm | Nhược điểm | Phù hợp với |
          |---|---|---|---|
          | **GitFlow** | Tách bạch nhiều phiên bản phát hành song song | Nhiều nhánh trung gian, dễ rối khi gộp | Hệ thống lớn, phát hành chậm theo tháng/quý |

          ## 2. Cấu Trúc Nhánh GitHub Flow Chi Tiết
          ```text
          main (luôn sẵn sàng đưa lên sản phẩm thật, khóa không cho đẩy trực tiếp)
            ├── feature/ABC-123-them-gio-hang   (nhánh tính năng mới)
            ├── fix/ABC-456-sua-loi-tinh-thue   (nhánh sửa lỗi)
            └── hotfix/ABC-789-khan-cap         (nhánh sửa lỗi khẩn cấp trên bản chạy thật)
          ```

          **Quy ước đặt tên nhánh:**
          - `feature/<mã-việc>-<mô-tả-ngắn>`: phát triển tính năng mới.
          - `fix/<mã-việc>-<mô-tả-ngắn>`: sửa lỗi phát hiện khi kiểm thử.
          - `hotfix/<mã-việc>-<mô-tả-ngắn>`: vá lỗi gấp trên môi trường thật.
          - `chore/<mô-tả-ngắn>`: cập nhật thư viện, cấu hình, tài liệu.

          ## 3. Quy Trình Pull Request (PR) Chuẩn 7 Bước
          1. Tách nhánh mới từ `main` mới nhất (`git checkout -b feature/...`).
          2. Viết mã và chia thành các commit nhỏ, nội dung rõ ràng (ví dụ: `feat: thêm nút thanh toán VietQR`).
          3. Đẩy nhánh lên kho chung và mở Pull Request (kèm mô tả ngắn gọn và ảnh chụp nếu sửa giao diện).
          4. Hệ thống CI/CD tự động chạy kiểm tra cú pháp (lint), kiểu dữ liệu và kiểm thử đơn vị.
          5. Ít nhất 1 thành viên khác đọc mã và bấm phê duyệt (Approve).
          6. Gộp vào `main` bằng chế độ **Squash and Merge** (gom các commit lẻ thành 1 commit sạch sẽ).
          7. Xóa nhánh tính năng sau khi đã gộp xong để giữ kho gọn gàng.

          ## 4. Chiến Lược Giải Quyết Xung Đột (Conflict)
          - **Ưu tiên cập nhật bằng `rebase`**: Khi nhánh `main` có thay đổi mới, kéo về và dựng lại nhánh tính năng lên trên `main` (`git fetch origin && git rebase origin/main`) thay vì gộp ngược `main` vào nhánh nhiều lần gây lịch sử chằng chịt.
          - **Lưu ý an toàn**: Chỉ chạy `rebase` trên nhánh cá nhân của bạn; tuyệt đối không `rebase` nhánh `main` dùng chung.
          - **Công cụ hỗ trợ**: Dùng trình xử lý xung đột trực quan của VS Code để chọn chính xác phần mã giữ lại, rồi chạy kiểm thử lại ngay.

          ## 5. Đánh Nhãn Phiên Bản (Tags) & Phát Hành
          - Đặt mã phiên bản theo chuẩn **SemVer** (`v1.2.3`: `1` = thay đổi lớn không tương thích ngược, `2` = thêm tính năng mới, `3` = sửa lỗi nhỏ).
          - Tạo bản phát hành (Release) trên GitHub hằng tuần kèm danh sách thay đổi tự động sinh từ tiêu đề các Pull Request đã gộp.
