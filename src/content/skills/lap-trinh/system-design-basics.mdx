          # Thiết Kế Hệ Thống: Dịch Vụ Rút Gọn Đường Dẫn (URL Shortener)

          ## 1. Làm Rõ Phạm Vi & Giả Định
          - **Trong phạm vi**: Rút gọn đường dẫn, chuyển hướng nhanh, đếm thống kê lượt bấm, đặt bí danh riêng và hẹn ngày hết hạn.
          - **Ngoài phạm vi**: Trang quản trị tài khoản doanh nghiệp, quét mã độc tự động theo thời gian thực.
          - **Giả định lưu lượng**: Hệ thống thiên về đọc rất mạnh (tỷ lệ đọc/ghi khoảng `100:1`), độ dài đường dẫn gốc tối đa `2.048 ký tự`.

          ## 2. Ước Lượng Nhanh Tài Nguyên
          - **Lưu lượng đọc (Read QPS)**: `10.000 yêu cầu/giây`.
          - **Lưu lượng ghi (Write QPS)**: `10.000 × (1/100) = 100 lượt tạo mới/giây`.
          - **Dung lượng lưu trữ**: `1 tỷ đường dẫn × (50 bytes mã + 200 bytes đường dẫn gốc + 50 bytes siêu dữ liệu) ≈ 300 GB`.
          - **Băng thông mạng**:
            - Đường ghi (Write inbound): `100 lượt/giây × 500 bytes/yêu cầu ≈ 50 KB/giây`.
            - Đường đọc (Read inbound & outbound): Giả sử mỗi yêu cầu HTTP và phản hồi chuyển hướng `302` kèm header `Location` có kích thước khoảng `500 bytes` → lưu lượng vào khoảng `10.000 × 500 bytes ≈ 5 MB/giây`, lưu lượng phản hồi ra khoảng `5 MB/giây` (cộng thêm dư tải lúc cao điểm có thể gấp 2-3 lần).
          - **Bộ nhớ đệm (Redis Cache)**: Lưu 20% đường dẫn nóng thường xuyên được bấm (`200 triệu bản ghi × 300 bytes ≈ 60 GB`) → sử dụng cụm Redis Cluster chia nhiều nút.

          ## 3. Thiết Kế API Cốt Lõi
          ```http
          POST /api/v1/shorten
          Body: { "longUrl": "https://example.com/bai-viet-rat-dai", "customAlias": "uu-dai", "expiresAt": "2026-12-31T23:59:59Z" }
          Response (201 Created): { "shortUrl": "https://shr.t/abc123", "expiresAt": "2026-12-31T23:59:59Z" }

          GET /{shortCode}
          Response: 302 Found (Header Location: longUrl) + gửi sự kiện đếm lượt bấm vào hàng đợi

          GET /api/v1/analytics/{shortCode}
          Response (200 OK): { "clicks": 1234, "referrers": { "facebook.com": 800 }, "countries": { "VN": 1100 } }
          ```

          **Vì sao dùng mã HTTP `302 Found` thay vì `301 Moved Permanently`?**
          Mã `301` báo trình duyệt và bộ nhớ đệm trung gian (CDN) ghi nhớ vĩnh viễn đích đến, nên từ lần bấm thứ hai trình duyệt tự nhảy thẳng mà không đi qua máy chủ nữa — khiến bộ đếm thống kê mất dữ liệu. Dùng **`302 Found`** (chuyển hướng tạm thời) giúp mọi lượt bấm đều đi qua API để thống kê chính xác.

          ## 4. Mô Hình Dữ Liệu
          **PostgreSQL (Lưu trữ bền vững cho đường ghi):**
          ```sql
          CREATE TABLE urls (
            id BIGSERIAL PRIMARY KEY,
            short_code VARCHAR(20) UNIQUE NOT NULL,
            long_url TEXT NOT NULL,
            custom_alias VARCHAR(50) UNIQUE,
            created_at TIMESTAMP DEFAULT NOW(),
            expires_at TIMESTAMP,
            click_count BIGINT DEFAULT 0,
            user_id BIGINT
          );
          CREATE INDEX idx_short_code ON urls(short_code);
          CREATE INDEX idx_custom_alias ON urls(custom_alias);
          CREATE INDEX idx_expires_at ON urls(expires_at) WHERE expires_at IS NOT NULL;
          ```

          **Redis (Lưu đệm tốc độ cao cho đường đọc):**
          - Khóa `url:{short_code}` → Lưu `{long_url, expires_at}`, thời gian sống (TTL) 24 giờ hoặc đến thời điểm hết hạn.

          ## 5. Kiến Trúc Tổng Thể
          ```mermaid
          graph LR
            Client[Người dùng] --> LB[Cân bằng tải LB]
            LB --> API[Máy chủ API]
            API --> Cache[(Cụm Redis Cache)]
            API --> DB[(PostgreSQL Chính + Bản sao)]
            API --> MQ[Hàng đợi Message Queue]
            MQ --> Worker[Dịch vụ xử lý thống kê]
            Worker --> OLAP[(ClickHouse Phân tích)]
            Cache -.->|Trượt Cache| DB
            DB -.->|Đồng bộ đọc| Replica[(Bản sao đọc)]
          ```

          **Luồng chuyển hướng (Đường đọc):**
          1. Trình duyệt gửi `GET /abc123` qua bộ cân bằng tải tới máy chủ API.
          2. API tra cứu khóa `url:abc123` trong Redis.
          3. **Trúng Cache (Hit)**: Trả về ngay `302 Found` tới đường dẫn gốc, đồng thời đẩy sự kiện đếm lượt bấm bất đồng bộ vào hàng đợi (Message Queue) để không làm chậm người dùng.
          4. **Trượt Cache (Miss)**: Truy vấn PostgreSQL → lưu lại vào Redis → trả về `302 Found` (nếu không tồn tại thì trả về `404`).

          **Luồng tạo liên kết (Đường ghi):**
          1. Người dùng gửi `POST /api/v1/shorten`.
          2. API kiểm tra định dạng URL hợp lệ, sinh mã ngắn không trùng lặp.
          3. Ghi vào PostgreSQL và làm nóng sẵn vào Redis.
          4. Trả về đường dẫn rút gọn.

          ## 6. Đi Sâu Kỹ Thuật Cốt Lõi
          - **Chiến lược Cache**: Dùng mô hình **Cache-aside** (API tự đọc/ghi Cache khi cần) kết hợp hết hạn ngẫu nhiên (±10% thời gian sống) để tránh tình trạng hàng nghìn yêu cầu cùng trượt Cache một lúc (thundering herd).
          - **Chia mảnh cơ sở dữ liệu (Sharding)**: Băm theo `short_code` chia đều ra 16 mảnh PostgreSQL (mỗi mảnh chỉ khoảng 20 GB), tra cứu trực tiếp đúng mảnh không cần truy vấn chéo.
          - **Sinh mã duy nhất**: Sinh mã định danh 64-bit phân tán (Snowflake ID) rồi mã hóa sang hệ cơ số 62 (`a-z`, `A-Z`, `0-9`) cho ra chuỗi ngắn gọn khoảng 7-11 ký tự không trùng lặp.

          ## 7. Điểm Nghẽn & Đánh Đổi Kiến Trúc
          | Điểm nghẽn tiềm ẩn | Giải pháp và đánh đổi |
          |---|---|
          | Bộ cân bằng tải bị lỗi đơn điểm | Chạy dự phòng đa vùng sẵn sàng (Multi-AZ Load Balancer) |
          | Ghi thống kê trực tiếp làm chậm cơ sở dữ liệu chính | Tách riêng qua hàng đợi tin nhắn và lưu vào kho phân tích ClickHouse (chấp nhận số liệu trễ vài giây) |
          | Đường dẫn lan truyền đột biến (Hot key) | Lưu thêm lớp đệm nhỏ trong bộ nhớ RAM của máy chủ API (In-memory cache) cho các liên kết quá nóng |
          | Trùng bí danh tùy chọn | Ràng buộc `UNIQUE` ở mức cơ sở dữ liệu và báo lỗi rõ ràng nếu đã có người đặt trước |
